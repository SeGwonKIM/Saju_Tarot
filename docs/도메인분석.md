## 1. 자기 도메인 전달 형식 (과제 원본)

**[도메인 맥락]**
나는 사주, 타로 상담 도메인 1년 차이고, 사주·타로 상담 결과를 정리해 고객에게 전달하는 작업을 자동화/정리하고 싶습니다.

**[네 동작 분석]**

1. **분해**: 생년월일시 입력 → 사주팔자(만세력) 계산 → 오행 분포 분석 → 대운·세운 흐름 정리 → 타로 카드 스프레드 결과 해석 → 종합 상담 코멘트 작성, 이렇게 여섯 조각으로 나눔
2. **패턴**: 고객 질문이 대부분 연애·직업·재물 세 가지 주제로 반복되고, 특정 오행(예: 수 과다, 목 부족 등)이 반복적으로 등장하는 패턴을 발견
3. **추상화**: 복잡한 사주·타로 해석 과정을 "이번 달 흐름 세 줄 요약 + 연애·직업·재물 카테고리별 조언 한 줄씩"이라는 본질만 남긴 형태로 압축
4. **알고리즘**: 생년월일시·타로 카드 입력 → 사주팔자/오행 계산 → 타로 결과와 결합 → 카테고리별(연애·직업·재물) 해석 생성 → 최종 상담 리포트 출력 순서로 처리

**[출력 요구]**
고객에게 바로 전달 가능한 상담 리포트 형식으로, 한국어로.

**[검증 기준]**
경력 5년 이상의 선배 역술인 1명이 "실제 고객에게 그대로 전달해도 되는 수준이다"라고 평가할 것.

## 2. 네 동작 → 실제 제품 구조 매핑

분해한 조각이 코드의 어디에 대응되는지 확정했다. **분해가 곧 모듈 경계이자 API 경계가 됐다.**

| 네 동작 | 구현 형태 | PRD 위치 |
|---|---|---|
| 분해 — 6조각 | 백엔드 6개 모듈 = 달력 변환 / 만세력 / 오행 / 대운·세운 / 타로 / 리포트 생성 | PRD §5.1, §8 |
| 패턴 — 반복 주제 | **재회운·상대방속마음·연애·재물·대인관계 5분류**를 화면·API·LLM 출력 스키마에 고정 (v2.12 개정, 아래 §2.1) | PRD §3.4, §6.1, §11.2 |
| 패턴 — 오행 과다/부족 | 판정 규칙 수치화: 과다 ≥40%, 부족 ≤5%, 무 0% | PRD §8.4 |
| 추상화 — 3줄 + 주제별 1줄 | LLM 출력 JSON 스키마로 강제(자유 서술 금지). 길이 상한: 흐름 3줄 + 조언 최대 5줄 | PRD §11.2 |
| 알고리즘 — 처리 순서 | 요청 파이프라인 그대로 | PRD §5.1 |
| 출력 요구 | 리포트 화면 9블록 + 면책 문구 | PRD §6.3 |
| 검증 기준 | 아래 §6에서 수치화 | PRD §16.2 |

### 2.1 '패턴' 항목 개정 — 3분류 → 5분류 (v2.12)

§1의 과제 원본에는 "연애·직업·재물 세 가지"로 적었다. **그 문장은 제출 원본이라 그대로 둔다.** 다만 설계를 진행하며 다시 보니 실제로 들어오는 질문의 분포가 달랐다.

| 원본 (v1.0) | 개정 (v2.12) |
|---|---|
| 연애 · 직업 · 재물 | **재회운 · 상대방속마음 · 연애 · 재물 · 대인관계** |

- **왜 바꿨나** — 상담에서 가장 많이 나오는 질문은 직업 전망이 아니라 **관계**였다. "다시 될까요"(재회운), "그 사람 마음이 어떤가요"(상대방속마음)가 질문의 다수를 차지한다. 원본의 '연애' 한 칸에 세 종류의 질문이 뭉쳐 있었던 셈이다.
- **직업을 뺀 이유** — 재물("수입")과 대인관계("직장에서 부딪힘")로 질문이 나뉘어 들어가고, 주제가 5개를 넘으면 "짧게 정리"라는 추상화 원칙이 무너진다.
- **설계에 미친 영향** — 주제마다 사주와 타로의 **판단 비중이 다르다.** 특히 상대방속마음은 상대의 사주가 없으니 타로 중심으로 읽고, 그 한계를 리포트에 밝혀야 한다. 자세한 비중표는 PRD §3.4.

> 빈칸을 채운 뒤에도 다시 고쳐야 할 칸이 나온다는 것 자체가 과제의 자기 점검 문구("빈 칸은 아직 또렷하게 생각하지 못한 부분")가 맞았다는 뜻이다.

## 3. 서비스 정의 (확정)

**한 줄** — 이름·생년월일·출생시각·양력/음력을 입력하면, 사주팔자와 타로를 결합해 **"이번 달 흐름 세 줄 + 고른 주제별 조언 한 줄씩"** 리포트를 즉시 만들어 주는 웹서비스. 주제는 **재회운·상대방속마음·연애·재물·대인관계** 다섯 가지다.

### 입력 (10개 필드)

| 필수 | 이름 · 성별 · 달력 구분(**양력/음력**) · 생년월일 · **출생시각**(24시각↔12지시 토글, "모름" 허용) · 개인정보 동의 |
|---|
| **선택** | 윤달(음력일 때만 노출) · 출생지(진태양시 보정) · 타로 방식 |

> **상담 주제**(5분류, 1~5개)는 v2.12에서 선택 → **필수**로 올렸다. 주제가 없으면 조언을 만들 수 없다.

> 성별은 선택이 아니라 **필수**다. 대운의 순행·역행이 성별로 갈리기 때문.

### 출력 (리포트)

**이번 달 흐름 3줄** → 주제별 조언(고른 주제만큼, 최대 5줄) → **타로 3장**(지금 놓인 자리 · 지금 할 수 있는 것 · 이대로 가면) → 원국 4주 → 오행 분포 → 계산 기준 표기 → 면책 문구

### 목표 효과

| 지표 | 현재 | 목표 |
|---|---|---|
| 상담 1건 준비 시간 | 20~40분 | **5분 이내** |
| 만세력 정확도 | 수작업 | 골든 테스트 100건 **100%** |
| 리포트 생성 | — | p95 **8초** |

## 4. 기술 선택 (강의 기준 적용 결과)

블로그 3강의 5축(AI 친화도·러닝커브·생태계·자료·유지보수)으로 후보를 좁혔다. **"많이 쓴다"와 "내 조건에 맞다"는 다른 질문**이라는 기준을 그대로 적용했다.

| 층 | 선택 | 한 줄 근거 |
|---|---|---|
| 프론트 | **React 19 + Vite + TS + Tailwind** | AI 코드 정확도 최상, 자료 최다. 화면 3개라 Next.js는 과함 |
| 백엔드 | **Python + FastAPI** | 만세력·절기 계산 라이브러리가 파이썬에 있고, Pydantic이 API 명세를 강제 |
| DB·인증 | **Supabase (RLS 필수)** | 관리형 Postgres + Auth. RLS 꺼지면 열린 DB |
| 해석 | **Claude API** | 단, **LLM은 계산을 하지 않는다** — 문장 생성만 |
| API 형식 | **REST** | 엔드포인트 8개, 응답 고정 → GraphQL 이점 없음 |
| 배포 | **Cloudflare Pages + Render + Supabase** | 3분할. Vercel Hobby는 개인·비상업용 제한이라 제외 |

### 백엔드가 필요한 이유 (강의 판단 기준)

> 여러 사람이 나눠 쓰거나 · 껐다 켜도 남아야 하거나 · **비밀이 오가면** → 서버가 필요하다.

LLM API 키가 오가고(비밀), 리포트를 저장·공유해야 한다(영속·공유). 지금까지 만든 게임 4개(ksk_game·drive_game·bom_game·ksk_game1)와 달리 **이 서비스는 화면-only가 아니다.**

## 5. 보안 원칙 (특별관리)

생년월일시 + 이름은 **개인 식별이 가능한 민감 정보**이고, LLM 키는 유출되면 곧바로 요금이 청구된다. 그래서 사람의 주의력이 아니라 **기계가 막는 구조**로 정했다.

| 원칙 | 실행 |
|---|---|
| 비밀값은 코드에 없다 | 환경변수만. `.env`는 `.gitignore`, 배포 플랫폼 설정 화면에 별도 입력 |
| 최우선 키는 로컬에도 없다 | `ANTHROPIC_API_KEY`·`SUPABASE_SERVICE_ROLE_KEY`는 운영 서버에만. 개발은 별도 dev 키 |
| 유출은 4중으로 막는다 | gitleaks pre-commit → GitHub Push Protection → CI 이력 스캔 → 부팅 시 환경변수 검증 |
| 유출되면 회전이 먼저다 | 커밋 삭제보다 **키 폐기(T+0)** 가 우선. 런북대로 T+15분 내 사용내역 확인 |
| 개인정보는 암호화해 저장 | 이름·생년월일시 AES-256-GCM, 목록은 `홍*동` 마스킹, **공유 링크에 이름 미표시 기본 ON** |
| 프론트는 못 믿는다 | 모든 검증을 서버에서 다시. 인증(401)과 인가(403)를 나눠 IDOR 차단 |
| RLS는 켠 뒤 정책을 쓴다 | 테이블 생성 SQL과 RLS 정책을 같은 마이그레이션 파일에 |
| 보관은 짧게 | 로그인 90일 / 비로그인 7일 자동 삭제, 로그에 이름·생년월일 미기록 |

> 블로그에 개발 과정을 기록하므로 **터미널 스크린샷에 환경변수가 찍히지 않는지** 매번 확인한다.

상세: PRD §12 (12.10 비밀값 대장 · 12.11 4중 방어 · 12.12 대응 런북 · 12.19 배포 전 체크리스트 14항)

## 6. 검증 기준 — 수치화

원본 [검증 기준]의 "그대로 전달해도 되는 수준"을 합격선으로 옮겼다.

| 평가 항목 | 척도 | 합격선 |
|---|---|---|
| 원국 4주가 정확한가 | 예/아니오 | **100%** |
| 오행 판정이 타당한가 | 5점 | 평균 4.0+ |
| 해석이 사주와 어긋나지 않는가 | 5점 | 평균 4.0+ |
| **"고객에게 그대로 전달해도 되는 수준"인가** | 예/부분수정/불가 | **'예' 70% 이상** |
| 위험 표현(단정·의료·투자) | 건수 | **0건** |

방법: 경력 5년 이상 선배 역술인 1명에게 **리포트 20건 블라인드 제시.** 계산 정확도는 별도로 KASI 기준 **골든 테스트 100건 100% 통과**가 릴리스 조건.
